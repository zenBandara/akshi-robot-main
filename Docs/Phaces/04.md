# Phase 04 — Edge Cases, Session Controls & Comprehensive Logging

> Handle every edge case gracefully — skips, breaks, teacher intervention, session recovery, multi-student queuing — and build the complete Firestore logging pipeline to record every interaction in detail.

---

## Part A — Skip Functionality (Deep Implementation)

### Step 1: Skip Key Binding
- [ ] In the Keyboard Manager, reserve the `S` key globally as "skip."
- [ ] The skip key should ONLY be active when `affordance_level == 3` (Level 3 control affordance).
- [ ] On all other levels, pressing `S` should do nothing (no feedback, no log).

### Step 2: Skip — Visual Prompt on Level 3
- [ ] On the Level 3 Evaluate Screen, display a styled "Skip" hint at the bottom: _"Press S to skip this question"_.
- [ ] Use a soft, non-distracting color so it doesn't pull focus from the question.
- [ ] Animate it in gently (fade-in after a 3-second delay so the child tries first).

### Step 3: Skip — Confirmation Dialog
- [ ] When `S` is pressed, show a brief on-screen confirmation: _"Are you sure? Press S again to skip, or any other key to stay."_
- [ ] Robot speaks: _"That's okay! Do you want to try another question?"_
- [ ] Wait for the second `S` press or a cancel key.

### Step 4: Skip — Record to State Manager
- [ ] In `state_manager`, add a `skipped_tasks` dictionary: `{ student_id: [task_id, task_id, ...] }`.
- [ ] On confirmed skip, append the current `task_id` to the student's skipped list.
- [ ] The student should never be asked the same task again in this session.

### Step 5: Skip — Update the Task Picker
- [ ] Modify `pick_random_task(exclude_ids)` to also exclude any tasks in the current student's `skipped_tasks`.
- [ ] If no more tasks are available for a student (all skipped), mark them as "completed with skips" and move on.

### Step 6: Skip — Navigate to Next Student
- [ ] After a skip, call `next_student()`.
- [ ] Robot speaks: _"No worries! Let's hear from someone else now!"_
- [ ] Transition to the Student Calling Screen with the next student.

### Step 7: Skip — Edge Case: All Tasks Skipped
- [ ] If a student has skipped every available task, show a gentle message: _"You've gone through all the questions! Great effort!"_
- [ ] Log this as `"all_tasks_skipped"` for the student.
- [ ] Proceed to the next student without error.

## Part B — Break Functionality (Deep Implementation)

### Step 8: Break Key Binding
- [ ] Reserve the `B` key as "take a break."
- [ ] The break key should ONLY be active when `affordance_level >= 2` (Level 2+ control affordance).
- [ ] On Level 1, pressing `B` does nothing.

### Step 9: Break Screen — Design
- [ ] Design a calming **Break Screen**:
  - Soft pastel background with gentle floating shapes (clouds, bubbles).
  - Text: _"Taking a little break... 🌿 Press Enter when you're ready to come back!"_
  - No timer, no pressure — the child decides when to return.
  - Soft ambient music or nature sounds loop (optional).

### Step 10: Break Screen — Implementation
- [ ] Create `screens/break_screen.py`.
- [ ] On entering the break screen, pause ALL timers (evaluation timer, if running).
- [ ] Store the complete current state snapshot: `affordance_level`, `5e_stage`, `cascade_position`, `current_task`, `current_student`.

### Step 11: Break — Robot Speech
- [ ] Robot speaks: _"Let's take a short break! You're doing amazing, [Name]!"_
- [ ] Use the child's name (Level 2+ affective affordance is active).

### Step 12: Break — Resume Flow
- [ ] On `Enter` press, restore the exact state snapshot.
- [ ] Resume all paused timers from where they left off.
- [ ] Navigate back to the exact screen the child was on before the break.
- [ ] Robot speaks: _"Welcome back, [Name]! Let's continue!"_

### Step 13: Break — Do NOT Mark as Finished
- [ ] Verify that taking a break does NOT remove the student from the queue.
- [ ] Verify the student's progress is fully intact after resuming.
- [ ] The child should continue exactly where they left off — not restart the cascade.

### Step 14: Break — Multiple Breaks
- [ ] Allow multiple breaks per student per task.
- [ ] Log each break event with a timestamp.
- [ ] Do not limit the number of breaks (preschool children need flexibility).

## Part C — Teacher Intervention (Deep Implementation)

### Step 15: Teacher Intervention — Trigger Condition
- [ ] Define the exact trigger: the student has failed the final Evaluate (Level 3) after the Engage stage.
- [ ] The cascade has been fully exhausted: `evaluate_L1 → elaborate → evaluate_L2 → explain → evaluate_L3 → explore → evaluate_L3 → engage → evaluate_L3 → FAIL`.
- [ ] Automatically transition to the Teacher Intervention Screen.

### Step 16: Teacher Intervention Screen — Design
- [ ] Calm, positive visuals (green/blue tones, NOT red/alarming).
- [ ] Message displayed for the teacher: _"Dear Teacher, [Student Name] needs a little extra help with '[Task Name]' 😊"_.
- [ ] Message displayed for the child: _"Great job trying! Your teacher is going to help you now!"_
- [ ] Prompt: _"Teacher, press C when ready to continue."_

### Step 17: Teacher Intervention — Robot Speech
- [ ] Robot speaks to the child first: _"You did wonderful trying, [Name]! Let's ask teacher for a little help."_
- [ ] Then to the teacher: _"[Teacher Name], could you help [Student Name] with this one?"_
- [ ] Maintain a 100% positive, encouraging tone — zero negative framing.

### Step 18: Teacher Intervention — Waiting State
- [ ] While waiting for `C` key, the screen stays static — no timers, no animations.
- [ ] The teacher has unlimited time to work with the child offline.
- [ ] Disable all other keyboard inputs except `C`.

### Step 19: Teacher Intervention — Continue
- [ ] On `C` press, mark this task as `"teacher_assisted"` for the student.
- [ ] Do NOT ask this student the same task again in this session.
- [ ] Call `next_student()`.
- [ ] Robot speaks: _"Thank you, teacher! Okay, let's see who's next!"_

### Step 20: Teacher Intervention — Log Detail
- [ ] Log the full cascade path ending with `"teacher_intervention"`.
- [ ] Record: student ID, task ID, teacher ID, affordance level reached (3), total time spent, number of attempts at each level.

## Part D — Session State & Multi-Student Queue Management

### Step 21: Student Queue — Data Structure
- [ ] Define the student queue as an ordered list with metadata per student:
  ```
  {
    student_id, student_name,
    status: "pending" | "in_progress" | "completed" | "skipped_all",
    assigned_tasks: [],
    completed_tasks: [],
    skipped_tasks: [],
    teacher_assisted_tasks: []
  }
  ```
- [ ] Store in `state_manager.student_queue`.

### Step 22: Student Queue — Rotation Logic
- [ ] After each student finishes (correct, skip, or teacher intervention), rotate to the next `"pending"` student.
- [ ] If the current student took a break, keep their status as `"in_progress"` and rotate to the next student OR stay (based on break behavior — stay with current student for break).
- [ ] When all students are `"completed"`, trigger Session Complete.

### Step 23: Student Queue — Prevent Duplicate Tasks
- [ ] Track all tasks assigned to each student (whether passed, failed, or skipped).
- [ ] When picking a new task for a student, exclude all previously assigned task IDs.
- [ ] If a student has been through all available tasks, mark as `"completed"`.

### Step 24: Session Recovery — Auto-Save State
- [ ] On every state change (screen transition, answer submitted, break taken), auto-save the session state to Firebase Realtime Database.
- [ ] Save under: `sessions/{session_id}/state`.
- [ ] Include: current student, current task, cascade position, affordance level, student queue.

### Step 25: Session Recovery — Resume on Crash
- [ ] On app startup, check Firebase for an active/incomplete session.
- [ ] If found, prompt: _"A previous session was interrupted. Press R to resume or N to start fresh."_
- [ ] On resume, restore the full state and navigate to the correct screen.

### Step 26: Session Recovery — Clean Exit
- [ ] When a session completes normally (all students finished), mark the session as `"completed"` in Firebase.
- [ ] Clear the auto-saved state to prevent stale resume prompts.

## Part E — Firestore Logging Pipeline

### Step 27: Firestore — Initialize Client
- [ ] In `firebase.py`, add Firestore client initialization alongside the existing Realtime DB.
- [ ] Use `firebase_admin.firestore` to get the Firestore client.
- [ ] Test the connection by writing a dummy document on startup.

### Step 28: Firestore — Log Schema Design
- [ ] Define the Firestore collection structure:
  - **Collection:** `sessions/{session_id}`
    - `teacher_id`, `date`, `start_time`, `end_time`, `status`
  - **Sub-collection:** `sessions/{session_id}/interactions/{interaction_id}`
    - `student_id`, `student_name`, `task_id`, `task_name`
    - `result`: `"correct"` | `"incorrect"` | `"skipped"` | `"teacher_assisted"`
    - `affordance_level_reached`: `1` | `2` | `3`
    - `cascade_path`: `["evaluate_L1", "elaborate", "evaluate_L2", ...]`
    - `total_attempts`, `time_spent_seconds`
    - `breaks_taken`: `[{timestamp, duration}]`
    - `timestamp`

### Step 29: Firestore — Create Session Document
- [ ] When a teacher is selected and the session begins, create a new session document.
- [ ] Auto-generate a `session_id` (UUID or timestamp-based).
- [ ] Record `teacher_id`, `date`, `start_time`, student count.

### Step 30: Firestore — Log Interaction on Correct Answer
- [ ] When a student answers correctly, write an interaction document:
  - `result: "correct"`, `affordance_level_reached`, full `cascade_path`.
  - Calculate `time_spent_seconds` from when the task started to the correct answer.
- [ ] Call `firebase.log_interaction(session_id, data)`.

### Step 31: Firestore — Log Interaction on Skip
- [ ] Write an interaction document with `result: "skipped"`.
- [ ] Record the exact cascade position when the skip occurred.
- [ ] Record the affordance level at time of skip.

### Step 32: Firestore — Log Interaction on Teacher Intervention
- [ ] Write an interaction document with `result: "teacher_assisted"`.
- [ ] Record the full cascade path (all 5E stages attempted).
- [ ] Record all attempts and time spent at each level.

### Step 33: Firestore — Log Break Events
- [ ] Each break taken is logged as a sub-event within the interaction document.
- [ ] Record: `break_start_timestamp`, `break_end_timestamp`, `break_duration_seconds`.

### Step 34: Firestore — Log Timeout Events
- [ ] When the timer expires on an Evaluate Screen, log it as `"timeout"` in the cascade path.
- [ ] Distinguish between `"incorrect"` (student chose wrong) and `"timeout"` (student didn't answer).

### Step 35: Firestore — End Session Document
- [ ] When the session completes (all students done), update the session document:
  - Set `end_time`, `status: "completed"`.
  - Record summary stats: total students, total tasks, average affordance level reached.

### Step 36: Firestore — Error Handling
- [ ] Wrap all Firestore writes in try/except blocks.
- [ ] If a write fails, log the error to console but do NOT crash the app.
- [ ] Queue failed writes for retry on next successful connection.

## Part F — Realtime Database Sync (Live Session State)

### Step 37: Realtime DB — Session Active Flag
- [ ] When a session starts, set `sessions/{teacher_id}/active = true` in Realtime DB.
- [ ] The web portal can read this to know a session is in progress.
- [ ] On session end, set `active = false`.

### Step 38: Realtime DB — Current Student Display
- [ ] Write the current student's name and task to Realtime DB: `sessions/{teacher_id}/current_student`.
- [ ] The web portal can display this live to the teacher.
- [ ] Update on every student rotation.

### Step 39: Realtime DB — Live Progress Counter
- [ ] Maintain a live counter: `students_completed / total_students`.
- [ ] Write to Realtime DB: `sessions/{teacher_id}/progress`.
- [ ] The web portal can show a progress bar.

### Step 40: Realtime DB — Listen for Teacher Commands (Future)
- [ ] Add a listener on `sessions/{teacher_id}/commands` for real-time commands from the web portal.
- [ ] Supported commands: `pause`, `resume`, `end_session`.
- [ ] For now, just set up the listener — implementation in a future phase.

## Part G — Task Assignment & History Tracking

### Step 41: Task History per Student
- [ ] Maintain a per-student task history in the State Manager:
  ```
  student_task_history = {
    student_id: [
      { task_id, result, affordance_level, cascade_path, timestamp }
    ]
  }
  ```
- [ ] Append to the history after every interaction (correct, skip, or teacher intervention).

### Step 42: Task Difficulty Tracking
- [ ] Track how many students got each task correct on the first attempt.
- [ ] Track the average affordance level reached per task.
- [ ] Store as: `task_stats = { task_id: { first_attempt_correct: int, avg_affordance: float } }`.
- [ ] This data can inform future dynamic task allocation.

### Step 43: Student Performance Summary
- [ ] At the end of a session, generate a per-student summary:
  - Total tasks attempted, tasks correct, tasks skipped, tasks needing teacher help.
  - Average affordance level reached.
  - Total time spent.
- [ ] Store in Firestore under the session document.

### Step 44: Session Summary Report
- [ ] At session end, generate an overall session summary:
  - Total duration, total students, total tasks.
  - Success rate (first-attempt corrects / total).
  - Most difficult task (highest avg affordance level).
  - Students needing most support.
- [ ] Store in Firestore and print to console.

## Part H — Error Handling & Robustness

### Step 45: Handle Missing Task Assets
- [ ] If a task JSON references an image that doesn't exist, display a placeholder image instead of crashing.
- [ ] Log a warning: _"Image not found: [path]. Using placeholder."_
- [ ] Create a cheerful placeholder image (e.g., a question mark with stars).

### Step 46: Handle Firebase Connection Loss
- [ ] Detect when Firebase is unreachable (both Realtime DB and Firestore).
- [ ] Switch to offline mode: continue the session using local state.
- [ ] Queue all log events locally in a temp file.
- [ ] When connection is restored, flush the queued events to Firebase.

### Step 47: Handle Empty Student List
- [ ] If the teacher's student list is empty, show a message: _"No students found! Please set up the class in the web portal."_
- [ ] Robot speaks the same message.
- [ ] Return to the Teacher Selection Screen.

### Step 48: Handle Empty Task Pool
- [ ] If no valid task JSONs are found in `Tasks/task_jsons/`, show: _"No tasks available! Please add tasks."_
- [ ] Log the error and prevent the session from starting.

### Step 49: Handle Corrupt Task JSON
- [ ] If a task JSON fails validation (missing fields, bad format), skip it and log a warning.
- [ ] Continue with the remaining valid tasks.
- [ ] If ALL tasks are corrupt, show the "no tasks available" message.

### Step 50: Graceful App Crash Recovery
- [ ] Wrap the main app loop in a global exception handler.
- [ ] On unhandled exception: save the current state to a crash recovery file, log the traceback.
- [ ] On next startup, offer to resume from the crash recovery state.
